# Spec Driven을 쉽게 이해하기

이 문서는 코드를 직접 쓰지 않는 업무 담당자를 위한 설명 자료입니다. 강사는 **오전 3H의 설명·시연**에서 이 문서와 [카운터 스펙](02_카운터_스펙.md)을 소개합니다. 카운터는 강사가 보여 주는 아주 작은 시연입니다. 학생은 **오후의 기존 체크리스트 실습**에 같은 원칙을 적용합니다. 뒤에 나오는 화장품 영업 회의록과 비용 보고서는 개념을 설명하는 예시이며, 학생이 추가로 만들어야 하는 실습이 아닙니다.

## 1. “만들어 줘” 다음에 무엇을 확인할까요?

“숫자가 올라가는 화면을 만들어 줘”라고 말하면 AI는 여러 선택을 해야 합니다. 처음 숫자는 0일까요, 1일까요? 버튼은 하나면 될까요? 새로고침하면 숫자를 보관할까요? 화면을 예쁘게 만들라는 뜻일까요, 버튼이 정확히 움직이는 것이 우선일까요? 사람에게는 당연한 내용도 프롬프트에는 빠져 있을 수 있습니다.

Spec Driven은 만들기 전에 **우리가 원하는 결과와 완료 기준을 문서로 적고, 그 문서를 계획·구현·검사의 기준으로 쓰는 방식**입니다. 여기서 스펙(spec)은 “무엇이 어떻게 되어야 하는가”를 정리한 약속입니다. AI가 알아서 좋은 결과를 추측하도록 두는 대신, 사람이 확인할 기준을 먼저 제공합니다. 문서를 길게 쓰는 것이 목표는 아닙니다. 같은 문장을 읽은 사람과 AI가 같은 결과를 예상할 수 있게 쓰는 것이 목표입니다.

## 2. 수업에서 따르는 순서

**의도 → 스펙 → 계획 → 사람 확인 → 구현 → 검사 → 수정**의 순서로 진행합니다.

1. **의도:** 지금 해결하려는 불편을 한 문장으로 말합니다. “버튼을 누른 횟수를 화면에서 바로 보고 싶다”처럼 사용 이유를 적습니다.
2. **스펙:** 대상·입력·동작·완료 조건·범위·예외를 적습니다. “화면이 좋다” 대신 “처음 열면 0, 버튼 한 번에 1 증가, 새로고침하면 0”처럼 관찰할 수 있게 씁니다.
3. **계획:** AI가 어떤 파일을 만들고 어떤 순서로 동작을 넣고 검사할지 설명합니다. 스펙은 원하는 결과, 계획은 그 결과를 만드는 방법입니다. 작은 카운터의 계획은 3줄 이내로 충분합니다.
4. **사람 확인:** 계획이 스펙과 맞는지 읽습니다. 저장 기능을 넣겠다는 계획이 나왔다면 “저장하지 않기로 했다”는 기준으로 바로 고칩니다. 미정인 내용을 AI가 확정했다면 구현 전에 확인합니다.
5. **구현:** 확인한 범위 안에서 파일을 만듭니다. 만들다가 새로운 기능을 추가하고 싶어지면 기존 완료 조건에 몰래 섞지 않고 별도 후보로 적습니다.
6. **검사:** 결과 파일을 열고 스펙에 적힌 동작을 실제로 해 봅니다. AI가 “완료”라고 말한 것과 우리가 버튼을 눌러 확인한 것은 구분합니다.
7. **수정:** 다르게 움직인 부분을 기준과 함께 알려 줍니다. “이상해”보다 “새로고침 뒤 0이어야 하는데 3이 남는다”가 수정할 위치를 분명하게 만듭니다. 수정 뒤에는 영향을 받은 동작을 다시 검사합니다.

## 3. 스펙의 여섯 칸

| 칸 | 사람이 답할 질문 | 카운터의 짧은 답 |
| --- | --- | --- |
| 대상 | 누가 어떤 상황에서 쓰나요? | 처음 버튼 동작을 확인하는 수강생 |
| 입력 | 사람이 무엇을 넣거나 누르나요? | 증가 버튼을 한 번 누름 |
| 동작 | 입력 뒤 무엇이 달라지나요? | 표시 숫자가 정확히 1 증가 |
| 완료 조건 | 무엇을 보면 통과인가요? | 시작 0, 한 번 누르면 1, 새로고침 뒤 0 |
| 범위 | 이번에 어디까지 만들까요? | HTML 파일 1개, 화면 1개 |
| 예외 | 예상 밖 상황은 어떻게 다룰까요? | 여러 번 누르면 매번 1 증가, 화면을 다시 열면 0 |

완료 조건은 가능하면 “입력 또는 행동 → 예상 결과”로 적습니다. 숫자를 보여 주는 도구라면 화면 색보다 값이 맞는지를 먼저 정합니다. 보고서를 만든다면 어느 파일과 어느 숫자를 근거로 판단할지도 정합니다. 예외를 모두 상상해서 수십 줄로 늘릴 필요는 없습니다. 현재 작은 범위에서 쉽게 생기는 상황부터 적습니다.

## 4. `.md`는 실행 프로그램이 아니라 텍스트 문서입니다

`.md`는 Markdown이라는 작성 형식의 문서 확장자입니다. `#`은 제목, `-`는 목록을 표시하지만 본문은 사람이 읽는 글입니다. 편집기로 열어 내용을 읽거나 고칠 수 있습니다. 스펙 파일을 저장한다고 카운터가 만들어지거나 보고서가 실행되지는 않습니다. 파일을 AI에게 읽게 하고, 계획을 확인하고, 실제 구현·실행을 해야 결과가 나옵니다.

스펙에 `output/demo/spec-counter.html`을 적어 둔 것은 결과 위치를 정한 것입니다. 그 이름을 쓰는 순간 HTML 파일이 자동으로 생기는 것은 아닙니다. 스펙 문서가 존재하는지, 결과 파일이 존재하는지, 결과가 실제로 맞는지는 각각 확인할 일입니다.

## 5. 스펙·CLAUDE.md·SKILL.md·프롬프트는 역할이 다릅니다

| 이름 | 맡는 역할 | 업무 말로 풀면 |
| --- | --- | --- |
| 스펙 | 이번에 만들 결과·범위·완료 조건 | 이번 의뢰의 요구사항 문서 |
| CLAUDE.md | 프로젝트에서 참고할 공통 규칙 | 원본 보존, 외부 공유 전 확인 같은 공통 업무 기준 |
| SKILL.md | 한 업무를 반복 수행하는 실행·검사 절차 | 주간 보고를 준비하고 검사하는 작업 순서 |
| 프롬프트 | 지금 AI에게 할 일을 알려 주는 문장 | “이 스펙을 읽고 계획부터 설명해 줘”라는 전달 문장 |

스펙과 다른 문서가 충돌하면 사람이 어떤 기준을 적용할지 정해야 합니다. 예를 들어 공통 규칙이 원본 보존인데 스펙에 원본 덮어쓰기가 적혀 있다면 구현 전에 충돌을 확인합니다. 스펙을 CLAUDE.md에 모두 복사하거나 문서를 SKILL.md로 이름만 바꾼다고 역할이 자동으로 같아지지 않습니다. 파일을 읽었다는 말만으로 실행·검사까지 완료되었다고 보지도 않습니다.

## 6. Claude Code에서 `@`로 로컬 문서를 참조하기

`@`는 **Claude Code 대화 안에서 파일을 참조하는 입력 방법**입니다. 터미널의 `cd`처럼 폴더를 이동하는 셸 명령이 아닙니다. `@templates/...`를 일반 셸에 실행하려고 붙여 넣지 않습니다. 먼저 현재 열린 작업 폴더가 `claude-work-lab`인지 확인합니다.

1. Claude Code의 대화 입력칸에 `@`를 입력합니다.
2. 경로 제안에서 `templates/spec-driven/02_카운터_스펙.md`를 찾습니다. 필요하면 경로 일부를 이어 입력합니다.
3. 해당 경로를 선택하고 **Enter 또는 Tab**으로 파일 선택을 확정합니다. 이때의 Enter는 경로를 고르는 단계입니다.
4. 파일 참조 뒤에 프롬프트 문장을 이어 적어 **프롬프트를 완성**합니다.
5. 완성한 문장을 읽고 **Enter로 전송**합니다. 파일 선택과 메시지 전송을 구분합니다.

강사 시연의 프롬프트 예시는 다음과 같습니다. 이것은 Claude 대화에 입력할 문장이며 셸 명령이 아닙니다.

```text
@templates/spec-driven/02_카운터_스펙.md를 읽고, 어떻게 만들지 3줄로 알려줘. 아직 만들지 마.
```

계획을 읽은 사람이 확인한 뒤 별도 메시지로 “계획을 확인했어. 이 스펙 범위대로 구현하고 검사항목 3개를 확인해 줘”라고 프롬프트를 보냅니다. 자동으로 다음 단계로 넘어갔다고 가정하지 않습니다. 경로가 제안되지 않으면 폴더와 실제 파일 위치를 확인하고, 다른 문서를 임의로 선택하지 않습니다. 작은 스펙을 읽은 뒤에는 핵심 조건을 말로 요약하게 해 기준이 전달되었는지도 확인할 수 있습니다.

이 입력 동선은 [Claude Code 공식 문서의 파일·폴더 참조 안내](https://code.claude.com/docs/en/common-workflows#reference-files-and-directories)를 참고했습니다. 설치된 화면에 따라 제안 목록의 모양은 달라질 수 있지만 파일 선택과 프롬프트 전송의 의미는 같습니다.

## 7. 시연 예시 — 아주 작은 카운터: 강사가 오전에 보여 줍니다

강사는 먼저 다른 대화에서 “버튼을 누르면 숫자가 올라가는 작은 카운터를 HTML 파일 하나로 만들어 줘. 결과는 output/demo/plain-counter.html에 저장해 줘”라는 직접 프롬프트를 보여 줍니다. 이후 별도의 대화에서 위 카운터 스펙을 참조해 `output/demo/spec-counter.html`을 만듭니다. 두 결과는 다른 파일이므로 한쪽 결과를 덮어쓰지 않습니다.

비교할 때는 버튼을 눌러 숫자가 어떻게 변하는지, 처음 값과 새로고침 결과가 무엇인지, AI가 확인하지 않은 내용을 어떻게 정했는지 봅니다. 직접 프롬프트에도 시작값·새로고침 동작을 자세히 적으면 스펙 프롬프트와 가까운 결과가 나올 수 있습니다. 이 시연의 두 프롬프트는 **제공한 정보량이 다르므로 문서 형식만의 효과를 공정하게 측정한 실험이 아닙니다.** 스펙 방식이 항상 더 좋은 결과를 만든다거나 짧은 프롬프트가 항상 실패한다고 결론내리지 않습니다. 설명이 짧아도 충분한 작은 일은 직접 프롬프트로 처리할 수 있습니다.

우리가 관찰할 것은 “기준을 적고 계획을 확인하니 무엇을 검사할지 분명해졌는가”입니다. 학생이 카운터 두 개를 추가로 제작하는 시간이 아닙니다.

## 8. 설명 예시 — 화장품 영업 회의록: 추가 실습이 아닙니다

의도는 “영업 회의 뒤 누가 무엇을 언제까지 할지 놓치지 않고 싶다”입니다. 스펙의 대상은 영업 담당자, 입력은 제공한 교육용 회의 메모 한 개입니다. 동작은 결정 사항·담당자·기한을 표로 정리하는 것입니다. 완료 조건은 원문에 나온 결정이 빠지지 않고, 없는 담당자나 날짜를 만들어 넣지 않는 것입니다. 범위는 회의록 문서 작성까지이며 거래처에 보내거나 고객 정보를 외부에 올리는 행동은 포함하지 않습니다.

예외도 간단히 적을 수 있습니다. 원문에 “다음주까지 샘플을 보내자”만 있고 담당자가 없다면 담당자를 **미정**으로 남기고 확인 질문을 씁니다. 제품명이나 날짜가 두 곳에서 다르면 어느 표현이 최종인지 사람에게 확인합니다. “보기 좋은 표가 나왔다”는 검사와 “원문에 없는 약속을 만들지 않았다”는 검사는 다릅니다. 원문 문장과 출력 표를 대조하는 것이 핵심입니다.

## 9. 설명 예시 — 비용 보고서: 추가 실습이 아닙니다

의도는 “이번 주 비용을 같은 기준으로 확인하고 동료가 읽을 요약을 만들고 싶다”입니다. 대상은 비용 마감 담당자, 입력은 교육용 Excel 사본, 동작은 입력 검사 후 합계·건수와 공유 문안을 만드는 것입니다. 완료 조건은 행의 숫자와 합계가 맞고 이번 검사가 통과한 것입니다. 범위는 제공 보고서 도구로 결과 파일을 만드는 것이며 회계 시스템 연동이나 메시지 발송까지 확장하지 않습니다.

원본의 기준은 40건·2,333,300원입니다. 제공 수정후 파일은 41건·2,363,300원이고 다음주 파일은 별도 입력으로 12건·1,130,900원입니다. 어느 입력을 골랐는지 먼저 확인한 뒤 그 입력에 맞는 숫자를 검사해야 합니다. 오류 입력이라면 마지막 정상 보고서가 남아 있어도 이번 `verification.json`의 `ok: false`를 실패로 읽습니다. 입력을 고치고 같은 도구를 다시 실행해 `ok: true`가 된 뒤 최신 결과를 사용합니다. 카드가 예쁘다는 사실이 숫자나 최신 상태가 맞다는 증거는 아닙니다.

## 10. 원문 기준·미정·수정 이력을 남기기

스펙을 쓸 때 “어디에서 나온 요구인지”를 같이 적습니다. 회의록은 제공한 회의 메모, 보고서는 선택한 Excel과 교안의 검사 기준, 작은 화면은 사용자가 확인한 요구가 기준입니다. AI의 추측을 원문에서 확인한 사실처럼 적지 않습니다.

확인하지 못한 항목은 `미정: 담당자 확인 필요`처럼 표시합니다. 미정인 내용이 완료 조건이나 범위에 영향을 주면 구현 전에 사람에게 묻습니다. 학생에게 새 웹검색이나 새 도구 설치를 시켜 빈칸을 채우는 단계는 이 수업에 없습니다. 제공 자료와 사용자의 답으로 먼저 작은 범위를 확정합니다.

기준을 바꾸려면 짧은 수정 이력을 남깁니다. 예를 들어 “초안: 새로고침 뒤 유지 여부 미정 → 사람 확인: 저장하지 않고 0으로 시작 → 확정본에 반영”이라고 씁니다. 나중에 숫자를 저장하고 싶어지면 새 요구로 기록하고 새 완료 조건을 정합니다. 기존의 ‘저장 없음’ 기준을 결과에 맞춰 지워 성공으로 처리하지 않습니다. 결과와 기준이 다를 때는 구현이 잘못된 것인지, 기준을 바꾸기로 한 것인지부터 구분합니다.

## 11. 오후 적용 — 기존 체크리스트의 스펙에 같은 원칙을 씁니다

오후 첫 개인 실습은 기존 체크리스트입니다. 카운터·회의록·비용 보고서 예시를 한 화면에 합치거나 새로운 실습을 추가하지 않습니다. 제공된 `templates/checklist-spec.md`를 읽고 대상, 입력, 동작, 완료 조건, 범위, 예외가 충분히 분명한지 봅니다. 필요한 개인 기준은 기존 실습의 수정 범위에 맞춰 적습니다.

처음부터 로그인·팀 공유·달력·자동 알림·DB 저장까지 넣으면 무엇이 잘못됐는지 확인하기 어렵습니다. 먼저 한 화면의 추가·완료 같은 핵심 동작을 완성하고 직접 검사합니다. 새로고침 후 저장 여부는 카운터의 기준을 복사하지 말고 **기존 체크리스트 스펙의 기준**을 읽습니다. 서로 다른 도구의 완료 조건을 섞지 않는 것도 스펙을 사용하는 방법입니다.

## 12. 빈칸 스펙 예시 — 필요할 때 사본에 채우는 틀

아래 틀은 생각을 정리하는 예시입니다. 모든 칸을 길게 채울 필요는 없고, 제공 실습과 관계없는 새 프로젝트를 시작할 필요도 없습니다.

```markdown
# [이번에 만들 아주 작은 결과]
- 의도: [어떤 불편을 줄이려는가]
- 원문 기준: [제공 자료 또는 사람이 확인한 요구]
- 대상: [누가 어떤 상황에서 쓰는가]
- 입력: [파일, 내용, 버튼 등]
- 동작: [입력 뒤 일어나는 일]
- 완료 조건: [행동 → 기대 결과를 2~3개]
- 결과 파일: [이번 실습의 출력 경로]
- 범위: [이번에 할 일 / 이번에 하지 않을 일]
- 예외: [현재 범위에서 예상되는 문제와 처리]
- 미정: [확인이 필요한 내용 / 없으면 없음]
- 수정 이력: [바꾼 기준과 사람이 확인한 이유]
```

## 13. 예쁜 출력과 기준 검증은 함께 보되 따로 판단합니다

화면을 읽기 쉽고 보기 좋게 만드는 것은 유용합니다. 하지만 디자인이 좋아도 버튼 한 번에 2가 증가하면 카운터 스펙은 통과하지 못합니다. 회의록 표가 깔끔해도 원문에 없는 담당자를 넣으면 업무 기준에 맞지 않습니다. 비용 보고서의 색이 멋져도 실패 입력의 결과를 최신 성공처럼 표시하면 사용할 수 없습니다.

검사할 때는 먼저 스펙의 완료 조건을 실제 행동으로 확인하고, 다음으로 글과 화면이 읽기 쉬운지 봅니다. 통과한 항목과 아직 확인하지 않은 항목을 구분해 기록합니다. 이번 강사 시연을 봤다는 사실만으로 내 체크리스트가 완성된 것은 아닙니다. 오후에는 내 결과 파일을 직접 열어 내 스펙의 동작을 확인합니다.

## 14. 참고 자료와 이 수업의 범위

[GitHub Spec Kit 공식 안내](https://github.github.com/spec-kit/)는 요구를 정리한 뒤 계획·구현·검증으로 이어가는 구조를 소개합니다. **이 자료는 그 개념을 채택한 단순 수업판**이며 Spec Kit 도구의 설치·명령·전체 절차를 실습하는 자료가 아닙니다. Spec Kit 설치, 새 MCP 연결, 학생의 웹검색을 요구하지 않습니다. 이미 제공한 로컬 문서와 Claude Code의 파일 참조로 스펙 → 짧은 계획 → 사람 확인 → 구현 → 검사를 경험합니다.

공식 출처는 강사가 확인할 참고 링크입니다. 학생은 링크를 검색해 도구를 추가하기보다 지금 실습의 원문과 완료 조건을 확인하면 됩니다. 문서를 늘리는 것보다 작은 결과 하나를 기준대로 만들고 검증하는 데 집중합니다.
